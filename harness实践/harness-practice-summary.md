# 博文学堂 Harness 实践总结

## 一、Harness 是什么

Harness 是博文学堂项目自定义的一套 **Agent 工程约束与自反馈体系**，其核心公式为：

> **Harness = 文档约束 + 自反馈闭环**

它不是一个外部工具或框架，而是一种面向 AI Agent 开发协作的项目治理模式。目标是让 Agent 在每次修改代码后能自主验证改动是否合规，形成 "改→验→修" 的闭环，减少对人工 review 的依赖。

---

## 二、Harness 体系的组成结构

整个 Harness 体系由四个层次构成：

```
┌───────────────────────────────────────────────────────────┐
│  Layer 1：导引入口（AGENTS.md）                            │
│  → Agent 进入项目时的唯一入口，索引所有知识文档             │
├───────────────────────────────────────────────────────────┤
│  Layer 2：知识文档（docs/agents/01~04）                    │
│  → 项目元信息 / 核心架构 / 工程约束 / 自反馈工作流         │
├───────────────────────────────────────────────────────────┤
│  Layer 3：自动注入规则（.catpaw/rules/）                   │
│  → 每次对话自动生效，不需要 Agent 主动查阅                 │
├───────────────────────────────────────────────────────────┤
│  Layer 4：自反馈 Linter（scripts/lint-project.sh）        │
│  → 代码修改后的自动化合规检查，零违规才算完成               │
└───────────────────────────────────────────────────────────┘
```

---

## 三、Layer 1 — 导引入口（AGENTS.md）

`AGENTS.md` 是 Agent 进入项目的唯一入口，职责包括：

- 一句话定位项目（O2O 家教撮合平台）
- 知识文档索引表，指明"什么时候看哪份文档"
- 执行计划目录结构说明
- 自动注入规则列表
- 核心约束速览（6 条速查清单）

设计哲学：Agent 不需要通读整个项目，只需先读 AGENTS.md，按需跳转对应文档。

### 4.3 工程约束（03-constraints.md）

这是 Harness 的"法律条文"，分 7 个板块：

1. **版本硬约束** — JDK 17 / Spring Boot 3.2.5 / jakarta.* / MyBatis-Plus Boot3 Starter / Knife4j Jakarta
2. **编码禁忌** — 禁止 javax.* / 禁止改 review_record / 禁止 Controller 写业务逻辑 / 禁止硬编码状态值
3. **命名规范** — DB snake_case / Java camelCase / API kebab-case / 类名 Xxx{Controller|Service|Mapper|DTO}
4. **状态流转规则** — 需求只能前进（例外：任意→CLOSED）；审核有严格回退路径
5. **业务硬规则** — 推荐上限 5 人、验证码频率限制、信息脱敏
6. **文档同步纪律** — 改表必改文档、改 API 必改注解、改流程必改图
7. **Git 提交规范** — `type(scope): 简述` 格式

### 4.4 自反馈工作流（04-workflow.md）

定义了执行计划机制和 Linter 反馈闭环流程，详见下文第五、六节。

## 五、Layer 3 — 自动注入规则

通过 `.catpaw/rules/` 目录，以下三份规则在每次 Agent 对话中自动生效：

| 规则文件 | 作用 | 生效范围 |
|---------|------|---------|
| `project-constraints.md` | 版本约束 + 编码禁忌 + 命名 + 业务规则 | `**/*.java, **/pom.xml` |
| `doc-maintenance.md` | 文档维护纪律：改代码必同步文档 | `**/*.java, **/*.sql, **/*.md` |
| `exec-plan-discipline.md` | 执行计划创建与完结纪律 | `**/*`（全局） |

关键设计：这些规则使用 `alwaysApply: true` 元数据，确保 Agent 无需记住"去看规则"这个动作，系统自动注入上下文。

## 六、Layer 4 — 自反馈 Linter

### 6.1 使用方式

```bash
bash scripts/lint-project.sh
```

### 6.2 检查项

| 编号 | 检查内容 | 级别 | 检查方式 |
|------|---------|------|---------|
| R1 | javax.* 包引用 | ERROR | grep 扫描 src 目录 |
| R2 | Spring Boot 版本锁定 (3.2.5) | ERROR | 解析 pom.xml |
| R3 | review_record 表 UPDATE/DELETE | ERROR | grep 关键词组合 |
| R4 | Controller 层 @Transactional | WARN | 定向扫描 controller 目录 |
| R5 | 硬编码状态值 (setStatus(数字)) | WARN | 正则模式匹配 |
| R6 | 推荐数量上限校验存在性 | WARN | 检查推荐相关代码中是否有 5/MAX_RECOMMEND |
| R7 | SQL 文件字符集 + 引擎检查 | ERROR/WARN | 检查 utf8mb4 和 InnoDB |

### 6.3 反馈闭环流程

```
Agent 修改代码
      ↓
运行 lint-project.sh
      ↓
┌─────────────┐    ┌─────────────┐
│  0 违规     │    │  有违规      │
│  → 完成     │    │  → 修复      │
└─────────────┘    └──────┬──────┘
                          ↓
                   再次运行 linter
                          ↓
                   直到 0 违规
```

### 6.4 退出码设计

- 返回 0：全部通过（可能有 WARN 但无 ERROR）
- 返回 非0：存在 ERROR，必须修复后才能继续

## 七、执行计划机制

### 7.1 何时需要执行计划

满足以下任一条件时，必须先创建执行计划再动手编码：

- 涉及 3 个以上文件的修改
- 新增一个完整功能模块（Entity + Mapper + Service + Controller 四件套）
- 数据库 DDL 变更
- 跨多层的重构

### 7.2 执行计划格式

```markdown
# 执行计划：<标题>

## 目标
一句话描述要做什么。

## 验收标准
- [ ] 标准1
- [ ] 标准2
- [ ] linter 零违规
- [ ] 编译通过

## 步骤
1. 步骤1
2. 步骤2

## 执行日志
- [时间] 完成了什么
- [时间] 遇到什么问题，如何解决
```

### 7.3 生命周期

```
创建 (active/) → 执行中（逐项完成验收标准，记录日志）→ 完成 (completed/) + 追加 activeLog
```

### 7.4 小改动豁免

修复 typo、单文件 bug fix、配置微调不需要执行计划。

## 九、Part 2 — 自反馈工作流与测试闭环

### 9.1 核心认知：编译通过 ≠ 功能生效

代码能编译，不等于功能真的生效。这是 Harness 必须建立的第二个子系统。

工程瓶颈很快会从"写代码"变成"验证结果"。UI、日志、指标、测试结果这些**运行态信息**，必须能直接被 Agent 读取和判断。如果只有文档约束没有自反馈闭环，Agent 最终还是会退化成代码打字机。

落到实践里，这件事可以概括成一句话：

> **Harness = 文档约束 + 自反馈闭环**
>
> 前者负责不跑偏，后者负责不盲写。

### 9.2 自反馈闭环的完整链路

我最后沉淀下来的固定闭环是：

```
代码 → commit/push → SCM构建 → 测试环境部署 → API Test → 查日志 → 不通过就修 → 重新部署
```

这条链路最终被写进了 `docs/agents/自反馈工作流.md`，而不是只存在脑子里。它的意义是：

- 不允许停在"代码看起来对"
- 必须走到"环境里真的跑过，并且有日志证据"

**When to read this**：当任务涉及"代码开发 → 发布测试版本 → 部署测试环境 → 发 API 请求 → 查日志 → 修代码复验"这一整套需要 runtime 验证的需求时阅读。特别适合：异步链路、回调链路、observer 埋点、错误码透传、产物字段、字段全链路透传。

**核心目标**：让 Agent 不停留在"代码看起来对"，而是走到"测试环境已验证、日志已证明代码确实生效"。

### 9.3 执行元信息作为唯一事实源

为了让 Agent 针对不同的需求对应着不同的环境，需要一份 `docs/exec-plans/active/当前活跃需求执行说明.md`。这里面钉死的不是业务逻辑，而是**这轮执行所需的环境事实**：

- 当前代码分支
- 执行顺序
- 推荐使用的 Skill
- 测试 IDL 分支和版本
- 测试 PSM
- 控制面 / Env / 集群
- 阻塞处理规则

这一层很关键。它把"运行时元信息"从聊天里的临时说明，升级成了**能统一读取的事实源**。当单个测试计划中的默认参数、历史参数或旧说明与本文档不一致时，以本文档为准。

### 9.4 实际闭环是怎么工作的

MVP 所有的接口最终都走过了这条链路：

```
本地 mvn compile/test → SCM 测试构建 → ENV 部署 → API Test 发真实请求 → 日志检索复验
                                                                              ↓
                                                              失败则改代码 → 重新部署 → 再测
```

真正能说明问题的，是中间两次典型的**运行态纠偏**：

**例子 1：API Test 打不通，不是代码错，而是 IDL/测试口径不一致**

一开始并不是代码直接失败，而是 API Test 平台使用的 schema 和服务实际运行的 IDL 口径不一致。如果没有自反馈闭环，这类问题很容易被误判成"服务没部署成功"或"handler 没命中"或"代码没生效"。但因为把"测试参数、IDL 分支、IDL 版本、PSM、环境"都前置写进了执行说明，所以最后能被定位成**测试入口口径问题**，而不是业务代码本身的问题。

**例子 2：线上日志打出 `Unknown column 'AIOId'`，倒逼 repo 层字段对齐真实 DDL**

这次最有代表性的运行态反馈，是查询链路第一次真正打到新 pod 后，日志里直接暴露了 `Unknown column 'AIOId' in 'where clause'`。这个问题**不可能靠"看代码感觉"发现**。它必须经过：1. 部署到真实环境 → 2. 发真实请求 → 3. 命中新 pod → 4. 定点查日志。最后才知道不是 IDL 问题也不是 handler 问题，而是 repo 层字段名和线上真实 DDL 没对齐。

这就是自反馈闭环真正的价值：**它不是帮你"更快确认自己是对的"，而是帮你更快发现自己到底错在哪。**

### 9.5 为什么执行日志对自反馈同样重要

如果没有执行日志，长任务跑一段时间之后，Agent 和人都会忘：这轮到底改了什么、测的是哪组参数、部署到了哪个版本、返回体是什么、上一轮失败的结论是什么。

所以要求每一步关键动作都写进 `activeLog.md` 和测试日志。这会带来两个直接收益：

1. 人睡觉的时候，Agent 还能继续工作
2. 人醒来之后，只要扫日志和测试结果，就能判断当前这一轮是否真的落地

### 9.6 自反馈工作流的可复制模板

如果你已经把 Part1 的文档和计划系统搭好了，接下来最小可复制的自反馈模板是：

1. **先写一份项目级 `自反馈工作流.md`** — 明确你的构建入口、部署入口、测试入口、日志入口
2. **为当前批次任务再写一份"执行说明"** — 把运行时元信息钉死（分支、环境、PSM、IDL 版本等）
3. **强制要求每一步关键动作写执行日志**
4. **不拿到运行态证据，就不允许把计划移到 `completed/`**

## 十、Part 3 — 对抗测试

### 10.1 核心认知：接口能跑通 ≠ 业务真的稳

对于一个需求，经过了自反馈验证不代表接口是稳定的。线上实际业务数据还没打过来，接口通不代表业务通。所以我们要**大量覆盖测试**。

### 10.2 对抗测试的工作模式

测试集不是我们自己手动出。工作模式是：

```
┌─────────────────────────────────────────────────────────────────┐
│  Agent A（对抗测试 Agent）                                       │
│  → 针对业务接口生成对抗测试数据集                                 │
│  → 列出对抗测试计划                                              │
└────────────────────────────┬────────────────────────────────────┘
                             ↓ 测试计划 + 测试数据集
┌─────────────────────────────────────────────────────────────────┐
│  Agent B（需求 Session Agent）                                   │
│  → 拿着测试计划和测试覆盖数据集跑自反馈                           │
│  → 遇到 bug 就修复重跑                                          │
│  → 直到所有数据集完成                                            │
└─────────────────────────────────────────────────────────────────┘
```

关键设计：**让出题者和解题者分离**，用一个 Agent 专门站在攻击者视角出对抗数据，另一个 Agent 负责跑通和修复。

### 10.3 对抗测试执行计划的结构

以"四接口线上联动与业务大范围验证执行计划"为例：

```markdown
# 四接口线上联动与业务大范围验证执行计划

## 状态
当前状态：执行中（可选值：待执行/执行中/完成）

## 执行记录要求
执行本计划时，记录拆成两层：
- 阶段级/里程碑级进展 → 记录到 docs/exec-plans/activeLog/activeLog.md
- case 级核心测试日志、请求响应、回查结果、bug 记录 → 记录到 activeTestLog.md

## 目的
本文档用于给本次四接口线上大范围测试提供唯一执行顺序，
统一测试参数和统一记录方式。

## 优先级规则
当单个测试计划中的默认参数、历史参数或旧说明与本文档不一致时，以本文档为准。
本文档是执行说明，不替代具体 case 清单、业务语义说明和修复细节。
```

### 10.4 对抗测试在 Harness 中的定位

对抗测试是 Harness 自反馈闭环的**最后一道防线**。完整的验证层次为：

```
Level 1: Linter 静态检查（秒级，编码合规性）
         ↓
Level 2: 编译通过 mvn compile（秒级，语法和依赖正确性）
         ↓
Level 3: 自反馈工作流（分钟级，单接口在真实环境跑通 + 日志证据）
         ↓
Level 4: 对抗测试（小时级，大量边界数据覆盖 + 多接口联动验证）
```

每一层解决不同的问题：Linter 保证不犯低级错误，编译保证语法正确，自反馈保证单接口能跑通，对抗测试保证业务场景全覆盖不回退。

## 十一、Harness 的核心设计原则

1. **文档驱动** — 所有规则都以 Markdown 文档形式存在，Agent 可直接解析理解
2. **分层递进** — 从导引入口到详细约束，Agent 按需深入，不信息过载
3. **自动注入** — 关键规则通过 .catpaw/rules/ 自动生效，不依赖 Agent 记忆
4. **即时反馈** — Linter 脚本提供秒级合规校验，形成"改→验→修"闭环
5. **强制纪律** — 执行计划制度确保多文件变更有序可追溯
6. **文档同步** — 代码和文档必须在同一次执行中一起更新，永不脱节
7. **渐进约束** — ERROR 必须修复，WARN 建议关注，避免阻碍开发效率
8. **运行态验证** — 编译通过只是起点，必须有真实环境 + 日志证据证明功能生效
9. **对抗覆盖** — 单接口跑通不够，必须有独立 Agent 生成边界数据做对抗测试
10. **出题与解题分离** — 对抗测试 Agent 和需求 Agent 角色分离，避免自我验证盲区
